# Phase 0 Discovery

## Purpose and status

This document records the current discovery baseline for EvidenceForge. It separates facts supplied in the project brief from assumptions that still need validation. It is a planning artifact, not customer research and not evidence of product-market fit.

**Status:** draft; no interviews or production measurements have been completed.

## Confirmed project constraints

The following are treated as confirmed requirements for this planning pass because they are explicit in the project brief:

- EvidenceForge is a local-first evidence-bound security questionnaire response workbench.
- The core behavior is evidence first, grounded draft, citations, human review, and export.
- Drafting must abstain explicitly when evidence is insufficient.
- The MVP includes a local workspace/account model, PDF/TXT/MD ingestion, single-sheet CSV/XLSX import, PostgreSQL plus pgvector, PostgreSQL full-text search, hybrid retrieval, reciprocal-rank fusion, one LLM provider, structured JSON, citations, review, export, evaluation, observability, Docker deployment, security controls, and an audit trail.
- OCR, web crawling, collaboration integrations, MCP, multi-provider routing, billing, automatic submission, enterprise SSO/SCIM, Kubernetes, fine-tuning, and autonomous provisioning are not to be implemented in the MVP.
- The bounded agent flow and review states are prescribed.
- The threat areas that must be addressed include prompt injection, cross-workspace leakage, malicious files, stale evidence, PII/log leakage, cost/DoS abuse, and authorization failures.
- The corpus must contain 60 cases with the specified category counts.
- Documentation must distinguish facts, assumptions, and future ideas and must not claim production security, customer validation, or measured performance.

## Working assumptions

These assumptions enable architecture work but require confirmation before implementation:

| ID | Assumption | Why it matters | Validation method |
|---|---|---|---|
| A-01 | The first deployment is operated by one organization or one trusted local team, rather than a public multi-tenant SaaS. | Sets the initial identity, storage, and operational boundary. | Interview deployment owner; document threat boundary. |
| A-02 | A workspace is the primary authorization boundary and users may belong to more than one workspace. | Determines every query predicate, export permission, and audit scope. | Confirm role and membership model with intended operator. |
| A-03 | Evidence owners can identify document title, source, owner, effective date, review date, and status. | Enables stale-evidence policy and useful citations. | Inspect representative evidence inventories. |
| A-04 | PDF text extraction is sufficient for MVP evidence; scanned/image-only PDFs are rejected or marked unsupported. | Avoids silently treating OCR quality as evidence. | Sample PDFs and measure extraction success. |
| A-05 | A single-sheet questionnaire has a stable question identifier and question text, with optional section and answer metadata. | Defines import validation and export mapping. | Collect sample CSV/XLSX files. |
| A-06 | The initial answer format can be represented as status, answer text, caveats, and citations, with optional reviewer notes. | Keeps the output schema narrow and testable. | Review five real answer formats. |
| A-07 | Human review is available before any output is used externally. | Makes `NEEDS_REVIEW` a real control rather than a UI label. | Confirm operating procedure and approval responsibility. |
| A-08 | The selected LLM provider supports structured output or a sufficiently constrained JSON response, and provider data handling is acceptable to the operator. | Affects schema validation, privacy controls, and provider selection. | Complete provider security and data-processing review. |
| A-09 | Local-first means the application and primary data can run on operator-controlled infrastructure; it does not necessarily mean air-gapped or offline. | Prevents a misleading security promise. | Define network and provider connectivity requirements. |
| A-10 | Vector embeddings can be generated by a permitted local or remote model without sending restricted evidence outside the approved boundary. | Affects architecture and privacy. | Classify evidence and choose embedding location. |
| A-11 | A reviewer can resolve conflicts and stale evidence; the system should surface, not adjudicate, them. | Avoids treating retrieval or model output as policy authority. | Interview reviewer; define escalation rules. |
| A-12 | The evaluation corpus can contain synthetic or sanitized documents rather than customer-sensitive content. | Makes repeatable testing possible without exposing PII. | Security review of corpus handling. |

## Users and jobs to be validated

### Primary user: security/compliance analyst

Job: answer a questionnaire efficiently using approved organizational evidence, while being able to explain where every assertion came from.

Needs:

- import questions without losing identifiers or ordering;
- search approved evidence by meaning and exact terms;
- see source metadata and bounded excerpts;
- receive a draft that distinguishes supported claims from unknowns;
- correct or reject the draft; and
- export only reviewed answers with traceable provenance.

### Secondary user: evidence owner or reviewer

Job: maintain evidence freshness and decide whether a draft is accurate enough to accept.

Needs:

- see evidence version, owner, effective/review dates, and source location;
- identify stale, conflicting, or superseded material;
- record review decisions and notes; and
- prevent unsupported claims from becoming accepted output.

### Operator/developer

Job: run the workbench locally, diagnose failures, and understand cost, latency, and safety behavior without exposing sensitive answer content in telemetry.

Needs:

- bounded jobs and retry behavior;
- redacted logs and useful metrics;
- auditable state transitions; and
- reproducible evaluation runs.

## Product hypotheses

These are hypotheses, not validated results:

1. Analysts will prefer an explicit abstention with actionable missing-evidence context over a fluent but unsupported answer.
2. Citation usability depends on showing source metadata and an excerpt, not just a document name.
3. Retrieval quality will vary materially by evidence type and question wording; hybrid lexical/vector retrieval will be more robust than either method alone.
4. A small, explainable state machine will be easier to review and secure than a free-form agent.
5. Reviewers need visible freshness and conflict signals to make a safe decision.

## Discovery questions

### Workflow and users

- Which questionnaire formats and answer types occur most often?
- Who is allowed to accept an answer, and can the person who drafts also accept it?
- What does “approved evidence” mean operationally? Is approval metadata in a source system or supplied manually?
- Is export used for internal review, customer response, auditor response, or all three?
- What is the expected size and frequency of a typical questionnaire run?

### Evidence and freshness

- Which document metadata is available and trustworthy?
- What makes a document stale: age threshold, superseded status, missing review, or a policy-specific rule?
- How should conflicting documents be presented and escalated?
- Are tables, headers, footers, appendices, and version histories important to meaning?
- Are any evidence classes prohibited from provider processing or from local logs?

### Identity and deployment

- Is the initial user model local accounts, an existing reverse proxy, or a single operator account?
- Are multiple workspaces required at MVP launch, or is a workspace model only a future isolation seam?
- Does local-first require no external network access, or is one approved LLM/embedding endpoint allowed?
- Who owns backups, key management, upgrades, and incident response?

### Output and evaluation

- What answer statuses and fields must match the target questionnaire?
- What level of citation granularity is useful: page, section, paragraph, or chunk?
- How should “ambiguous” differ from “insufficient evidence” in the UI and export?
- What is the gold standard for groundedness and citation correctness?
- Which latency and cost targets are acceptable for an analyst's workflow?

## Proposed discovery activities

1. Review three representative questionnaires and at least ten sanitized evidence documents.
2. Conduct three structured interviews: analyst, reviewer/evidence owner, and deployment operator.
3. Run a document extraction spike on representative PDFs, including tables and image-only files, without adding OCR to scope.
4. Define a small answer/citation rubric and have two reviewers label an initial sample independently.
5. Confirm data classification and provider boundary before sending any content to an LLM or embedding service.
6. Revisit all assumptions and promote only validated ones into implementation requirements.

## Decision gates before application code

- **G1 — Input contract:** sample questionnaire and evidence schemas are approved.
- **G2 — Authorization boundary:** workspace membership, roles, and export permissions are explicit.
- **G3 — Data boundary:** provider, embedding, storage, retention, and redaction decisions are approved.
- **G4 — Evidence policy:** freshness, conflict, unsupported file, and citation rules are written down.
- **G5 — Evaluation readiness:** the 60-case corpus format and gold labels are agreed.

## Product validation gate

Architecture approval does not establish product demand.

Before implementing LLM generation or expanding beyond the non-LLM vertical slice, validate the target workflow with real practitioners.

EvidenceForge proceeds only if:

1. At least three target practitioners or teams handle recurring security questionnaires.

2. At least two independently report the same concrete manual pain that the MVP addresses.

3. At least one participant agrees to review or test a sanitized artifact or workflow.

4. The target workflow does not depend on portal automation, enterprise SSO, or a large integration surface for its basic value.

5. Human review remains acceptable as the final authority.

6. A competing workflow/tool is identified and the specific gap EvidenceForge addresses is documented.

A “sounds useful” response does not count as validation.

If these conditions are not met, narrow or change the workflow before implementing the LLM layer.

## Unresolved questions

1. What exact roles are needed for the first deployment, and may a reviewer accept their own draft?
2. Is authentication in scope for the MVP or supplied by an operator-controlled proxy?
3. Is remote LLM/embedding access permitted for all evidence classes, some classes, or none?
4. What is the maximum file size, page count, run size, and concurrent job count that fit the local deployment?
5. What is the freshness policy for each evidence type, and can the system safely rank stale material lower without hiding it?
6. Which PDF structures must be preserved for citation accuracy?
7. Should ambiguous evidence produce a draft with an `AMBIGUOUS` status, or only `INSUFFICIENT_EVIDENCE` with an ambiguity reason?
8. Does export need to preserve original row order, columns, formulas, formatting, and question identifiers?
9. What reviewer actions and notes are legally or operationally required in the audit trail?
10. What LLM provider and model are allowed after privacy, retention, structured-output, and cost review?
11. How will secrets be supplied in Docker without committing them or exposing them in logs?
12. What backup and deletion guarantees are expected for local evidence and audit records?

## Risks requiring validation

- A seemingly local deployment may still send sensitive content to a remote provider.
- PDF extraction may change meaning or citation location, especially around tables and headers.
- A workspace model without complete query scoping can create a severe cross-workspace leak.
- A structured answer can be schema-valid but factually unsupported; schema validation is not groundedness.
- “Stale” and “conflicting” are policy judgments that retrieval alone cannot resolve.
- Small local machines may be vulnerable to oversized files, very large questionnaires, or expensive model calls.
- Evaluation labels may encode the same assumptions the system is meant to test.

## Phase 0 conclusion

The MVP is sufficiently bounded for a vertical slice, but the security boundary, data-provider boundary, freshness policy, and human approval workflow must be confirmed before generation is implemented. The next step should be the smallest evidence-and-citation path described in the README, with authorization and auditability built in rather than retrofitted.
